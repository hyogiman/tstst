## 0. 사용 방법 (3단계)

1. **5장 '결정사항' 표의 '확정' 칸을 채웁니다.** 비워 두면 '권장값'으로 진행됩니다.
2. **`docs/prompts/`의 프롬프트를 번호 순서대로 하나씩 AI에게 요청합니다.**
   - Claude Code(이 저장소)에서는 이렇게 요청하면 됩니다: `docs/prompts/04-bugfix-records.md 내용대로 진행해줘`
   - ChatGPT처럼 저장소를 직접 읽지 못하는 도구에는 `00-common.md` + 해당 번호 프롬프트 + 관련 HTML 파일을 함께 붙여 넣습니다.
3. **각 배치가 끝날 때마다 AI가 준 '실제 Firebase 확인 체크리스트'를 직접 확인합니다.** 가능하면 강사(아내분)가 직접 써 보게 합니다.

## 2. 우선순위 원칙

1. **되돌릴 수 없는 피해가 먼저입니다.** 기록 손상, 다른 학생·차시에 잘못 전달 → 소통 누락 → 통계 오해 → 불편 → 확장 순서입니다.
2. **"첫날부터 기록하지 않으면 영영 없는 데이터"는 개강 전에 해야 합니다.** 최초 제출 시각, 제출 이력, 응시 당시의 퀴즈 버전, 수강 기간은 나중에 코드를 고쳐도 과거 기록이 생기지 않습니다. 아직 수업 전이라면 지금이 데이터 구조를 바꾸기 가장 싼 시점입니다.
3. **AI가 스스로 검증할 수 있는 환경을 먼저 만듭니다.** 테스트 하네스(01)를 만들어 두면 이후 모든 수정이 "고쳤다고 말하는 것"이 아니라 "테스트로 확인된 것"이 됩니다.
4. **새 화면을 늘리기 전에 기록과 상태 전환을 안정시킵니다.** (ChatGPT 보고서의 결론과 같습니다.)

**왜 이 순서인가**
- **01을 맨 앞에 둔 이유:** 운영 Firebase를 건드리지 않고, AI가 수정 전 버그 재현과 수정 후 통과를 직접 확인할 수 있게 하기 위해서입니다. ChatGPT가 이번 검토에서 쓴 모의 환경 방식을 저장소에 남기는 것입니다.
- **03을 버그 수정보다 앞에 둔 이유:** 04·05 버그 수정의 상당수(모달, 시간 표시, 녹음기)가 두 파일에 복사된 공통 코드에 있습니다. 복사본이 이미 다섯 군데 이상 서로 달라졌기 때문에(N3), 먼저 합치면 한 번만 고치면 됩니다. 단, 03은 기능 변화가 없는 작업이니 **빨리 버그부터 잡고 싶다면 04 → 05 → 03 순서도 가능**합니다. 모든 프롬프트는 두 순서 모두에서 동작하게 작성했습니다.
- **06을 대시보드보다 앞에 둔 이유:** 대시보드의 '정시 제출률', '과거 차시 대상자', '재검토 대기'는 06에서 만드는 기록이 있어야 정확해집니다.
- **12(디자인 정리)를 뒤에 둔 이유:** 화면 기능이 어느 정도 확정된 뒤에 한 번에 정리해야 재작업이 없습니다. 그 전까지는 새 CSS 레이어를 덧붙이지 않는 규칙(00 공통 머리말)으로 더 나빠지지 않게 막습니다.
- **개강 준비 완료선:** 최소 02, 04, 05, 06, 07은 개강 전에 마치기를 권합니다. 08은 학생이 화면에 익숙해지기 전에 하는 편이 낫습니다.

| D3 | '제출 권장일'을 통계 마감으로 쓸지, 마감 후 제출 허용 여부 | **통계 마감으로 사용, 마감 후 제출 허용(‘늦은 제출’ 표시)** | 소규모 성인 강좌에서 제출 자체를 막을 이유가 적음 | 제출 권장일은 **통계 마감으로 쓰지 않음**. 통계는 **실시간**(현재까지 제출 현황)으로 보여 줌. 늦은 제출도 인정(구분 표시 불필요) |
| D4 | 한 학생이 동시에 여러 반을 들을 수 있나 | **아니오 — 한 학생 한 활성 반** | 현재 화면 구조가 반 1개 기준 | 동시에 **한 반만** 수강(유료·수준별 강의). 단, 반을 마친 학생은 **다음 반에 추가 입과 가능** |
| D5 | 퀴즈 점수의 용도 | **자율 복습용** (현재 구조 유지, 점수 위조 가능성은 문서로 명시) | 평가·수료에 반영하려면 서버 채점이 필요하고, Cloud Functions는 유료(Blaze) 요금제가 필요 | 자율 복습용. 단 강사의 **난이도 조절을 위해 퀴즈 점수 통계는 필요** → 문항 분석(P4-01)을 P2로 상향 |
| D6 | 학생 하단 메뉴 | 실제 수강생 데이터가 없으면 **B안: 홈 · 과제 · 복습 · 질문 · 내 정보** (예습은 홈의 '다음 수업 준비'로, '우리 반'은 내 정보로) / 있으면 A안: 과제 · 복습 · 다음차시 · 질문 · 내 정보 + 상단 요약 | 학생이 들어오자마자 할 일을 봄 | 실제 데이터 없음 → **B안**(홈 · 과제 · 복습 · 질문 · 내 정보) |
| D7 | 지금 실제 수강생 데이터가 있나 | (사용자 확인 필요) | 없으면 구버전 호환 코드·데이터 이전 작업을 대부분 생략 가능 | **실제 수강생 데이터 없음** (개강까지 시간 여유) → 데이터 이전 작업 생략, 구버전 호환 코드 정리 가능 |
| D8 | '다음차시 안내'의 의미 | **N차시 문서의 '예습' = N차시 수업 전에 볼 자료**로 변경 (D7 = 없음일 때) | 차시 선택기와 내용이 일치, "수업 전·후" 구조와 맞음 | 권장값 동의 (N차시 문서의 예습 = N차시 수업 전 자료) |
| D9 | 수업 영상 보관 | **유튜브 '일부 공개' 링크 임베드 병행**, 직접 업로드는 짧은 클립(예: 200MB 이하)으로 제한 | Storage 저장·전송 비용, 업로드 실패 위험 | 복습용 **강의 전체 영상**을 올릴 예정 → 직접 업로드 용량을 크게(Blaze 요금제 사용 중). 비용 절감 검토를 위해 **유튜브 '일부 공개' 링크 임베드도 병행** |

## 6. 사람이 직접 해야 할 일 (AI가 대신할 수 없는 것)

1. **결정사항 확정** (5장)
2. **02 보안 규칙 배치 전:** Firebase 콘솔 → Firestore Database → '규칙' 탭 전체 복사, Storage → '규칙' 탭 복사 → 저장소의 `firestore.rules.current`, `storage.rules.current` 파일로 붙여 넣거나 대화창에 전달
3. **개발용 Firebase 프로젝트 하나 더 만들기 (권장):** 개강 후에는 운영 데이터를 보호하기 위해 개발·운영 프로젝트를 나누는 것이 Firebase가 권하는 방식입니다. 지금 만들어 두면 이후 테스트가 안전합니다.
4. **각 배치 후 실제 기기 확인:** 특히 녹음·재생은 iPhone Safari, Android Chrome, **카카오톡 등 앱 내 브라우저**에서 따로 확인하세요. 앱 내 브라우저에서는 마이크 권한이나 녹음이 제한될 수 있습니다. 안 되면 '기본 브라우저로 열기' 안내 문구를 넣어야 합니다.
5. **보안 규칙 배포와 사이트 배포** (AI는 명령어만 제시)
6. **강사(아내분)의 실사용 확인 + 시범 수업:** 개강 전 지인 1~2명을 학생으로 초대해 한 차시(예습 → 출석 → 과제 → 피드백 → 질문)를 실제로 돌려 보면, 테스트로는 찾기 어려운 동선 문제가 드러납니다.
