# tstst 스페인어 교육관리시스템 검토 보고서

검토일: 2026-10-29 · 대상: 쎄뇨라유 스페인어 · 작성 목적: 기능·화면 흐름·학습분석 개선안

## 1. 검토 범위와 전체 판단

[검토한 저장소](https://github.com/hyogiman/tstst)는 강사 페이지 `admin.html`과 수강생 페이지 `index.html`을 중심으로 구성되어 있다. 기준 커밋은 [`cd043b95`](https://github.com/hyogiman/tstst/tree/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66)이다. 이 보고서의 코드 링크는 해당 커밋에 고정했다.

**소규모 스페인어 수업에 필요한 기능과 브랜드 방향은 갖춰져 있다. 다음 개발의 우선순위는 학습 기록을 정확히 보존하고, 강사가 처리할 일을 놓치지 않게 만들며, 통계의 대상과 시점을 명확히 하는 것이다.**

과제·음성 제출, 반복 퀴즈, 개별 피드백, 질문 대화, 출결, 반 이동까지 들어 있어 기능 범위는 충분하다. PC의 학생 목록과 상세 패널, 절제된 브랜드 색상, 카드 기반 정보 구분도 유지할 만하다. 반면 화면을 이동할 때의 초안 보존, 재제출과 재질문의 상태 변화, 과거 기록의 해석에서 중요한 문제가 확인됐다.

### 확인 방법과 해석 범위

- 저장소의 HTML·CSS·JavaScript와 파일 구성을 검토했다. 원본 두 페이지의 JavaScript 문법 검사는 통과했다.
- 복사한 페이지에서 Firebase 호출을 메모리 기반 모의 구현으로 교체하고, 가상 수강생 4명·12차시로 클라이언트 동작을 검증했다.
- PC 화면과 320·390·768 CSS px 폭의 화면을 확인했다. 좁은 화면 검증은 iframe을 통한 반응형 배치 확인이며, 실제 스마트폰의 키보드·마이크·재생 호환성 검증은 아니다.
- 실제 수강생 정보, 운영 Firebase 데이터, 실제 로그인·업로드는 사용하지 않았다. 저장소와 운영 서비스는 수정하지 않았다.
- **‘재현’은 이 로컬 모의 환경에서 동작을 확인했다는 뜻이다. ‘코드 확인’은 관련 구현에서 위험 조건을 찾았다는 뜻이다. 운영 Firebase의 권한·동시성·네트워크 특성까지 검증했다는 의미는 아니다.**

## 2. 현재 구성에서 유지할 부분

|---|---|---|
| 수강생 과제 | 텍스트·음성 제출, 이전 제출 내용, 강사 피드백을 한 화면에서 확인 | 재제출 이력, 초안, 새 피드백의 우선 노출 |
| 복습 | 단일·복수·O/X 문항, 해설, 첫 점수와 최근 점수, 반복 응시 기록 | 문제 버전 보존, 문항별 분석, 완료 후 화면 |

## 3. 실제 수업 전에 우선 수정할 문제

아래 ‘우선 수정’은 운영 중요도이며, 보안 취약점 등급을 뜻하지 않는다.

### F01. 출결 재저장이 지각·인정결석을 결석으로 바꾼다 — 재현

**현재 동작:** 빠른 출석 화면은 `present`만 체크 상태로 표시한다. 저장할 때 모든 학생을 체크 여부에 따라 `present` 또는 `absent`로 다시 저장한다.

**재현:** 지각 1명·인정결석 1명이 있는 차시에서 아무것도 바꾸지 않고 저장 → 두 학생 모두 결석으로 변경됐다. 확인창에는 결석 인원이 나오지만, 이미 분류한 예외 상태를 유지해 주지는 않는다.

**영향:** 출결 이력이 손상되고 학생 화면과 출석 통계도 잘못 바뀐다.

**수정:** 출석·지각·결석·인정결석·미입력을 명시적으로 구분한다. 빠른 체크를 유지하더라도 변경하지 않은 기존 상태는 보존하고, ‘남은 미입력을 결석으로 확정’하는 행동은 따로 둔다.

**완료 기준:** 각 상태가 섞인 차시를 수정 없이 저장해도 기존 상태가 보존된다. 한 명만 변경했을 때 다른 학생의 기록은 바뀌지 않는다.

근거: [출석 표시·저장 구현, admin.html:1198](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/admin.html#L1198)

### F02. 다른 차시에 선택한 음성이 새 피드백에 붙는다 — 재현

**현재 동작:** 강사 음성 초안의 키가 ‘제출 종류 + 학생 UID’로만 구성된다. 반·차시가 포함되지 않는다.

**재현:** 1차시 학생 A에게 줄 `week1-audio.webm`을 선택 → 저장하지 않고 2차시로 이동 → 같은 학생에게 텍스트 피드백만 입력해 등록 → 1차시 음성이 2차시 피드백 경로에 업로드됐다. 새 화면에서 해당 파일이 계속 선택되어 있음을 명확히 보여 주지도 않는다.

**영향:** 학생에게 다른 수업의 피드백을 전달할 수 있다.

**수정:** 초안을 강사·반·차시·제출 종류·학생별로 구분한다. 선택 파일과 대상 학생·차시를 등록 직전까지 보여 주고 취소 기능을 제공한다. 화면 이동과 로그아웃 때 녹음과 임시 상태를 정리한다.

**완료 기준:** 다른 차시·반·학생으로 이동해도 음성이 섞이지 않으며, 보존된 초안은 해당 대상 화면에서만 표시된다.

근거: [음성 초안과 피드백 등록, admin.html:1103](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/admin.html#L1103)

### F03. 화면 이동으로 작성 중인 내용이 사라진다 — 세 경로 재현

다음 경로에서 저장하지 않은 내용이 소실됐다.

1. 강사가 차시 과제 제목을 수정 → 다른 차시 선택 → 원래 차시로 복귀.
2. 강사가 학생 A의 피드백 입력 → 학생 B 선택 → A로 복귀.
3. 학생이 과제 답안을 수정 → ‘다음차시’ 탭 → 과제로 복귀.

학생 답안은 이전 제출 내용으로 돌아갔고, 강사 피드백 입력창은 비었다.

**수정:** 반·차시·학생·입력 영역별 초안 저장과 ‘저장 중 / 임시 저장됨 / 미저장 변경’ 표시를 넣는다. 보존할 수 없는 이동에는 이탈 확인을 둔다. 텍스트와 음성 파일은 따로 관리하고, 같은 기기의 다른 계정에 초안이 보이지 않도록 로그아웃 정리 정책을 정한다.

**완료 기준:** 탭·학생·차시 전환 후 초안이 복원된다. 새로고침 복구 범위를 명시한다. 이전 학생의 초안이 다른 학생에게 보이지 않는다.

근거: [차시 편집 전환, admin.html:867](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/admin.html#L867), [피드백 상세 재생성, admin.html:1087](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/admin.html#L1087), [학생 과제 렌더링, index.html:527](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/index.html#L527)

### F04. 답변 완료 질문에 추가 질문을 해도 계속 완료로 남는다 — 재현

**현재 동작:** 학생의 추가 답장은 하위 replies에만 저장하고 상위 질문의 상태를 갱신하지 않는다.

**재현:** 답변 완료된 질문에 학생이 다시 질문 → 상위 상태가 `answered`로 유지됐다. 대시보드의 미답변 집계는 이 질문을 놓친다.

강사 답변 후 저장 상태는 완료인데 열린 상세 화면의 배지와 버튼은 ‘답변 대기 / 답변 완료 표시’로 남는 문제도 재현됐다.

**수정:** 답장 저장과 함께 `needsTeacherReply`, `lastMessageAt`, `lastSenderRole`을 원자적으로 갱신한다. 질문은 최초 작성일보다 최근 대화순으로 보여 주고, 선택된 상세 화면의 상태도 갱신한다. 필요하면 역할별 마지막 읽은 시점으로 새 답장 배지를 만든다.

**완료 기준:** 학생 추가 질문 → 강사 대기 목록과 개수에 반영 → 강사 답변 → 목록과 상세 모두 완료 상태가 된다. 단순 감사 답장도 우선 확인 대상으로 올린 뒤 강사가 종료할 수 있다.

근거: [학생 추가 답장, index.html:669](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/index.html#L669), [강사 답변, admin.html:1182](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/admin.html#L1182)

### F05. 과제를 다시 내도 과거 피드백 때문에 ‘피드백 완료’로 취급된다 — 재현 + 코드 확인

**현재 동작:** 재제출은 같은 문서의 답안과 제출 시각을 덮어쓰지만 기존 피드백은 보존한다. 강사 화면은 피드백이 하나라도 있으면 완료로 판단한다.

**재현:** 피드백이 있는 답안을 수정해 재제출 → 새 답안과 기존 피드백이 같은 문서에 남고, 제출 버전을 구별할 값은 없었다.

**영향:** 선생님이 재제출을 놓치고, 기존 피드백이 어떤 답안에 대한 것인지 알기 어렵다. 최초 제출 시각도 덮어써져 정시 제출률을 나중에 정확하게 계산할 수 없다.

**수정:** 제출 회차를 보존한다. 최소한 `currentRevision`, `reviewedRevision`, `firstSubmittedAt`, `latestSubmittedAt`을 관리하고 피드백에 대상 revision을 기록한다. 권장 구조는 변경 불가능한 제출 이력과 현재 상태 요약을 분리하는 것이다.

**완료 기준:** 피드백 후 재제출하면 ‘재제출·재검토 대기’로 보인다. 이전 답안과 피드백의 연결이 유지된다. 최초 제출 시각이 변하지 않는다.

근거: [과제 재제출, index.html:541](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/index.html#L541), [피드백 완료 판정, admin.html:1076](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/admin.html#L1076)

### F06. 퀴즈를 수정하면 과거 답안의 의미가 달라질 수 있다 — 코드 확인

**현재 동작:** 응시 기록은 답안의 숫자 인덱스와 점수·문항 수 등을 저장하지만 문제 버전이나 당시 문항·보기 스냅샷은 저장하지 않는다. 강사의 이력 화면은 현재 퀴즈를 이용해 과거 답안을 해석한다. 코드에도 문제 수정 시 과거 해석이 달라질 수 있다는 안내가 있다.

**영향:** 보기 순서를 바꾸거나 문제를 교체한 뒤, 예전 답안이 다른 보기의 선택처럼 보일 수 있다. 총점 기록이 남아 있어도 문항별 오답 분석과 전후 비교의 신뢰성이 떨어진다.

**수정:** `quizVersion`과 안정적인 questionId·optionId를 기록하고 버전별 문제를 보존하거나, 응시 시점의 문제·보기·정답을 스냅샷으로 저장한다. 기존 기록은 버전 미상으로 구분하고, 새로운 문항별 분석에 무조건 섞지 않는다.

**완료 기준:** 문제 문구·보기 순서·정답·문항 수를 변경해도 이전 응시 화면과 해석이 바뀌지 않는다.

근거: [응시 저장, index.html:601](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/index.html#L601), [이력 표시, admin.html:1092](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/admin.html#L1092)

## 4. 함께 다듬을 세부 구현

| 항목 | 확인 수준·현재 문제 | 권장 변경 |

| 강사 메모 줄바꿈 | **재현.** 여러 줄 입력창에서도 Enter를 누르면 저장되고 창이 닫힘 | textarea에서는 Enter로 줄바꿈. 저장 버튼 또는 Ctrl/Cmd+Enter 사용 |

## 5. 현재 대시보드의 통계 해석부터 고칠 부분

집계 구현은 [admin.html:713](https://github.com/hyogiman/tstst/blob/cd043b95caf9678f4d5b5b89ec4ec55fe0757a66/admin.html#L713)부터 확인할 수 있다.

### 5.1 과제 제출률: 공개한 전체 과제와 현재 해야 할 과제가 섞여 있다

현재 분모는 ‘현재 수강생 수 × 공개되고 활성화된 과제 수’다. 마감 전 과제나 미래 차시를 미리 공개하면 제출률이 낮아진다.

검증용 데이터에서는 학생 4명, 공개 과제 6개, 제출 12건으로 **50% = 12/24**가 나왔다. 이 중 이미 진행한 4차시만 대상으로 비교하면 **75% = 12/16**이다. 이 숫자는 실제 반의 성적이 아니라 분모 차이를 보여 주는 가상 사례다.

현재 계산 자체는 ‘전체 공개 과제 대비 제출’이라는 정의로는 맞다. 다만 강사가 현재 이행 상황으로 읽기 쉽다. 다음 세 상태를 구분하는 편이 유용하다.

- 마감 완료 과제: 정시 제출·늦은 제출·미제출.
- 진행 중 과제: 제출 여부와 마감까지 남은 시간.
- 예정 과제: 학습 이행률 분모에서 제외.

‘제출 권장일’을 실제 통계 마감으로 사용할지도 먼저 정해야 한다. 권장일과 강제 마감일은 같은 개념이 아니다.

### 5.2 출석률: 미입력이 많아도 100%가 나올 수 있다

현재는 (출석+지각)/(출석+지각+결석)이며 인정결석과 미입력은 제외한다. 정책으로 선택할 수 있는 계산 방식이지만 입력 완성도를 함께 보여 줘야 한다.

가상 데이터의 완료된 4차시에는 학생·차시 조합 16개 중 출석 4, 지각 4, 인정결석 4, 미입력 4가 있었다. 화면 출석률은 **100% = 8/8**이었다. 동시에 **출결 입력 12/16**, 미입력 4건을 보여 줬다면 이 수치의 한계를 이해할 수 있다.

권장 표시: ‘출석·지각률 100% · 대상 8건’과 ‘출결 입력 75% · 12/16건’. 인정결석 처리 정책은 설명에 남긴다. 수업 종료 전 차시는 미입력 경고에서 제외한다.

### 5.3 ‘최근 8차시’가 최근 진행한 수업을 뜻하지 않는다

전체 차시 배열의 마지막 8개를 사용한다. 12차시를 미리 등록한 검증 사례에서 활동이 있는 1~4차시가 빠지고, 기록 없는 5~12차시가 차트에 표시됐다.

진행·완료한 차시를 먼저 필터링한 다음 최근 8개를 선택해야 한다. 예정 차시까지 보려면 별도 ‘전체 일정’ 보기로 제공한다.

### 5.4 현재 수강생 기준을 과거 차시에도 적용한다

현재 active 학생만 과거 집계에도 사용한다. 중도 등록·중지·반 이동에 따라 예전 수업의 분모와 실적이 달라질 수 있다. 하단 집계 설명만으로 학습 이력의 안정성을 확보할 수는 없다.

차시별 배정 대상 명단을 보존하거나 수강 유효 기간을 기록한다. ‘그 수업 때 대상이었는가’를 기준으로 집계하고, 미배정·면제·기록 없음·미제출을 분리한다. 기존 데이터에서 알 수 없는 배정 이력은 추정치로 명시한다.

### 5.5 첫 정답률은 좋은 시작이며 참여율을 함께 봐야 한다

현재 지표는 응시한 학생·차시별 첫 정답률의 평균이다. 적게 참여해도 응시자들의 점수가 높으면 반 전체가 잘 따라오는 것처럼 보일 수 있다.

예: ‘첫 정답률 67% · 응시 3/4명’처럼 평균과 참여 인원을 함께 보여 준다. 여러 차시를 합산할 때는 ‘학생 3명 / 학생·차시 12건’처럼 단위를 구분한다. 미응시는 학습 수준 0점으로 처리하지 않는다.

## 6. 학습분석에 추가하면 가치가 큰 지표

홈에는 아래 전부를 넣지 않는다. 우선 처리할 일, 핵심 학습 지표, 학생별 진행표를 배치하고 문항·학생 상세 분석은 클릭해서 들어가게 한다.

| 우선순위 | 지표·화면 | 강사의 판단과 행동 | 필요한 데이터·주의점 |
|---|---|---|---|
| 1 | 처리 대기: 미검토 제출, 재제출, 답변 대기, 출결 미입력 | 수업 전후 무엇부터 처리할지 결정 | 현재 자료로 시작 가능. F04·F05 상태 수정 필요. 숫자를 누르면 해당 필터로 이동 |
| 1 | 학생 × 차시 진행표 | 특정 학생의 연속 미제출·미응시를 빠르게 확인 | 최근 완료 4~8차시. 미배정·기한 전·미입력·미제출 구분. 색 외에 기호·문자 사용 |
| 1 | 첫 퀴즈 점수 + 참여율 | 어려웠던 수업과 참여하지 못한 학생을 구분 | 동일한 대상·기간으로 분모 고정. 학생 수와 응시 건수 표시 |
| 2 | 문항별 오답률과 학습 목표별 약점 | 다음 수업에서 다시 설명할 표현을 선택 | 문제 버전·문항 ID·학습 목표 태그. 최초 응시 기준으로 집계하고 n명 표시 |

| 3 | 며칠 뒤 다시 푸는 짧은 확인 문제 | 즉시 정답 기억과 시간이 지난 뒤의 이해를 구분 | 같은 학습 목표의 다른 문항, 확인 시점 기록 |

### 작은 반에 맞는 분석 원칙

1. **퍼센트 옆에 인원·건수를 함께 표시한다.** 4명 반에서는 1명이 25%p를 바꾼다.
2. **반 평균과 개인 추이를 함께 본다.** 평균 상승만으로 모든 학생이 향상됐다고 판단하지 않는다.
3. **반복 응시를 독립 학생처럼 더하지 않는다.** 문항 분석은 첫 응시, 최신 응시 등 기준을 명시한다.
4. **전후 점수 차이는 곧바로 실력 향상으로 단정하지 않는다.** 같은 정답을 외웠을 가능성이 있다. 일정 시간 후 새 문항이나 말하기 과제로 확인한다.
5. **‘주의 학생’은 설명 가능한 확인 신호로만 쓴다.** 예를 들어 ‘마감된 배정 과제 2회 연속 미제출’. 자동 낙인·등수·근거 없는 위험 점수는 우선순위가 낮다.
6. **접속 시간·클릭 수보다 과제·대화·표현 결과를 우선한다.** 페이지를 열었다는 것과 학습했다는 것은 다르다.

### 스페인어 수업에 특히 맞는 추가 내용

**말하기·쓰기 평가 기준:** 과제 수행, 의미 전달·이해 가능성, 문법, 어휘의 4개 항목을 0~3 또는 1~4 수준으로 간단히 정의한다. 발음은 억양의 ‘원어민 유사도’보다 전달의 명료성에 초점을 둔다. 점수와 함께 다음 시도의 구체적 목표 한 줄을 남긴다. 평가하지 않은 항목은 0점으로 채우지 않는다.

**학습 목표 태그:** ‘자기소개’, ‘카페 주문’, ‘ser/estar’, ‘성·수 일치’, ‘의문문’처럼 수업에서 실제로 다루는 항목을 붙인다. 대시보드는 ‘어떤 항목을 다시 가르칠까’에 답하게 한다. 문항 수가 적은 항목은 낮은 점수만 보고 확정적인 진단을 하지 않는다.

**개인 포트폴리오:** 첫 수업의 30~60초 자기소개와 이후 녹음을 나란히 듣고, 같은 평가 기준으로 짧게 비교한다. 학생에게는 ‘다음에는 연결 표현을 2개 써보기’처럼 바로 실행할 수 있는 목표를 보여 준다. 정식 언어 등급으로 자동 환산하지 않는다.

**예습 확인:** 필요하면 자료 확인 버튼이나 짧은 확인 문제를 추가한다. 영상 재생 클릭만으로 예습 완료를 선언하지 않는다. 열람 기록은 ‘확인했다’는 운영 정보로 제한해 해석한다.

## 7. 화면 구성과 UI 흐름 제안

### 7.1 강사 대시보드: 수업 전후 행동이 먼저 보이게

권장 화면 순서는 다음과 같다.

| 위에서 아래로 | 표시 내용 | 인터랙션 |
|---|---|---|
| 상단 한 줄 | 반 · 현재 차시 · 집계 기간 · 마지막 갱신 | 반/차시/기간 변경 |
| 처리할 일 | 피드백 대기 · 재제출 · 새 질문 · 출결 미입력 | 클릭하면 기존 관리 화면의 해당 목록으로 이동 |
| 핵심 지표 | 출석률+입력률 · 마감 과제 이행률 · 첫 퀴즈 점수+참여율 | 분모·기간·누락 설명 |
| 진행표 | 최근 완료 차시별 학생 현황 | 학생 또는 차시 상세 열기 |
| 상세 분석 진입 | 문항별 약점 · 학생 포트폴리오 | 별도 화면/패널에서 확인 |

기존 대시보드는 작성·편집 기능을 관리 메뉴로 분리하고 있다. 이 구조를 유지하면서 ‘대기 3건’을 누르면 바로 필터된 업무 화면으로 가도록 연결하면 된다. 대시보드 자체에 편집 폼까지 늘릴 필요는 없다.

운영 클래스 수·수강생 수는 맥락 정보로 작게 둬도 충분하다. 모바일에서는 로고가 있는 상단과 대형 브랜드 배너가 반복되어 주요 숫자까지 내려가는 길이가 길다. 대시보드 배너를 축소하면 실무 정보가 훨씬 빨리 보인다.

### 7.2 학생 첫 화면: 이번 차시에 할 일과 받은 피드백

지금은 ‘과제’가 기본 화면이고, 제출한 과제도 다시 편집하는 폼을 먼저 보게 된다. 새 피드백은 아래로 내려가야 한다.

작은 변경부터 적용한다.

- 상단에 ‘이번 수업: 5차시 / 과제 미제출 / 복습 완료 / 새 피드백 1개’ 같은 짧은 요약을 둔다.
- 이미 제출했다면 제출 내용 요약과 새 피드백을 먼저 보여 준다.
- 수정은 ‘수정해서 다시 제출’ 버튼을 눌러 시작하도록 한다.
- 피드백 확인 뒤 ‘수정해 보기’ 또는 ‘이 부분 질문하기’로 연결한다.
- 과제·질문에 차시와 제목을 연결해 학생과 강사가 맥락을 다시 설명하지 않게 한다.

메뉴를 전면 개편한다면 ‘홈 / 학습 / 질문 / 내 정보’의 4개 구조도 가능하다. 다만 첫 수정에서는 기존 메뉴를 유지하고 ‘우리 반’을 내 정보의 반 정보로 옮겨 5개로 줄이는 편이 변경 부담이 작다. 이름 목록만 제공하는 ‘우리 반’은 현재 핵심 학습 동선에 비해 비중이 크다.

### 7.3 복습: 이미 푼 학생에게 결과와 다음 행동을

복습 화면 진입 시 새 퀴즈를 바로 시작하는 대신, 이미 응시한 학생에게는 최근 결과·첫 결과·틀린 항목을 먼저 보여 준다. ‘오답 다시 보기 / 전체 다시 풀기’를 선택하게 한다. 중간에 나갔다 돌아올 때의 풀이 초안도 보존한다.

반복 응시 횟수를 학습 성취 자체로 강조하기보다, ‘이번에는 어떤 표현을 이해했는가’를 짧게 알려 주는 것이 스페인어 학습 목적에 맞는다.

### 7.4 강사 콘텐츠 작성: 저장·공개 상태를 분명하게

주차 공개, 과제·복습·예습 활성화, 저장 등 여러 제어를 조합해야 한다. 강사가 현재 학생에게 무엇이 보이는지 확신할 수 있어야 한다.

- 용어를 사용자 수업 단위에 맞춰 ‘차시’로 통일한다.
- ‘비공개 초안 / 저장됨 / 학생에게 공개됨’을 구분해 표시한다.
- 하단 고정 저장 영역에 미저장 여부와 저장 버튼을 둔다.
- 학생 화면 미리보기와 이전 차시 복사 기능을 제공한다.
- ‘다음차시’ 자료에는 대상 차시와 수업 날짜를 명시한다. 현재 선택 차시의 예습인지, 그 다음 수업 준비인지 혼동되지 않게 한다.
- 고급 서식 도구는 펼침 영역으로 두고 자주 쓰는 제목·설명·파일부터 보여 준다.

### 7.5 학생별 종합 화면은 추가할 가치가 있다

현재 기능별로 흩어진 정보를 ‘학생 한 명’ 기준으로 보는 화면이 유용하다.

학생 기본 정보 → 최근 4~8차시 출결·과제·복습 → 최근 피드백과 질문 → 강사 메모 → 다음 학습 목표 순으로 구성한다. 강사 메모는 학생에게 공개되는 피드백과 데이터·권한·표시를 명확히 분리한다.

학습 분석의 결과가 이 학생 화면으로 연결되면 강사가 통계를 보고 바로 지도를 이어갈 수 있다.

## 8. 디자인과 접근성 세부 제안

**전체적인 인상:** 조잡하다고 볼 정도로 무질서하지 않다. 브랜드 색과 여백, 카드 모양은 일관적이다. 복잡하게 느껴지는 원인은 장식 자체보다 반복되는 상단 영역, 비슷한 중요도로 나열된 상태와 조작, 화면마다 긴 설명이다.

| 대상 | 관찰·제안 |
|---|---|
| 모바일 강사 메뉴 | 가로 스크롤 메뉴에서 일부 기능이 화면 밖에 있다. 현재 메뉴 표시를 선명하게 하고 자주 쓰는 출결·피드백 접근을 짧게 만든다 |
| 넓은 관리 표 | 내부 가로 스크롤로 화면 전체 넘침은 피하지만 오른쪽 조작이 멀다. 모바일은 학생 카드+더보기 메뉴, 또는 이름 열 고정을 검토한다 |
| 하단 학생 메뉴 | 6개 항목이 작은 폭에 모여 있다. 핵심 학습 기능 중심으로 줄이고 선택 상태를 문자·아이콘 모두로 명확히 한다 |
| 보조 글자 | 일부 10~12px 설명과 옅은 회색 글자는 읽기 부담이 있다. 중요한 상태·기한은 본문에 가까운 크기와 대비로 올린다 |
| 상태 색 | 브랜드 붉은색 계열이 여러 상태에 반복된다. 완료·대기·오류를 아이콘·문자와 함께 구분하고, 삭제는 위험 동작으로 독립시킨다 |
| 버튼 크기 | 모바일 주요 터치 영역은 44px 안팎을 실용적 목표로 삼는다. WCAG 2.2 AA의 최소 기준은 예외 조건을 포함한 24×24 CSS px이므로 ‘44px가 법정/AA 최소’라고 표현하지 않는다 |
| 입력 라벨 | 일부 차시 선택·답안·파일 입력은 시각적 설명이 있어도 연결된 label 또는 접근 가능한 이름이 없다. for/id 또는 aria-label을 연결한다 |
| 모달 | aria-modal만으로는 부족하다. 열릴 때 포커스 이동, 내부 포커스 순환, 닫힌 뒤 원래 버튼으로 복귀를 구현한다 |
| 업로드 문구 | 기본 브라우저의 ‘Choose File’에만 의존하지 않고 ‘음성 파일 선택’ 같은 일관된 한국어 버튼과 파일명을 제공한다 |
| 오류·설정 안내 | 일반 학생 화면에 Firestore, Rules, Storage, Firebase UID 등 개발 용어가 나오는 부분을 정리한다. 학생에게는 현재 상태와 재시도·강사 문의 방법을, 운영자에게는 별도 진단 정보를 보여 준다 |

320·390·768px에서 확인한 테스트 화면은 페이지 전체가 크게 가로로 넘치지는 않았다. 그렇다고 모든 실제 기기에서 문제가 없다는 의미는 아니다. 긴 이름·긴 스페인어 문장·브라우저 확대·가상 키보드가 열린 상태는 다음 단계 검증 대상으로 남긴다.

접근성 참고: [W3C WCAG 2.2 Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

## 9. Firebase 권한과 운영 안정성: 별도 확인이 필요한 영역

저장소에는 운영 Firestore Rules·Storage Rules·인덱스·Firebase 배포 설정이 포함되어 있지 않았다. 따라서 **보안이 취약하다고 단정할 수 없으며, 반대로 안전하다고 확인할 수도 없다.**

UI의 강사 역할 검사와 학생별 조회 조건은 확인했다. 실제 권한은 배포된 Rules로 강제되는지 확인해야 한다. 특히 다음 경우를 에뮬레이터에서 구분해 검사하는 것이 좋다.

| 주체·상황 | 기대 결과 |
|---|---|
| 로그인하지 않은 사용자 | 비공개 반·과제·개인 기록 접근 거부 |
| 학생 A가 학생 B의 제출·퀴즈·질문·답장 경로에 접근 | 읽기·쓰기 거부 |
| 학생이 자기 users 문서의 role 또는 강사 피드백을 변경 | 허용한 필드 외 변경 거부 |
| 학생이 다른 반이나 중지·보관된 반에 제출 | 수강 정책에 맞게 거부 |
| 학생이 강사 개인 메모나 다른 학생 이메일 접근 | 거부 |
| 공개 반 명단 | 허용된 이름·별명 등 최소 정보만 읽을 수 있음 |
| 음성·자료 업로드 | 해당 반·학생·경로 권한과 허용 크기·유형 검증 |
| 강사 | 허용된 운영 범위의 조회·작성 정상 처리 |

Firebase는 문서 읽기를 허용하면 그 문서의 특정 필드만 Rules로 가려 제공하는 방식은 지원하지 않는다. 공개 정보와 비공개 정보는 문서를 분리해야 한다. 쓰기는 변경 가능한 필드를 제한할 수 있다. 현재 별도 members·teacherNotes 구조는 이 원칙에 맞춰 검증할 수 있는 기반이다.

또한 현재 퀴즈 정답과 채점 로직은 클라이언트에 있다. 자율 복습 도구로는 수용할 수 있는 선택이다. 공식 평가·수료 판단에 점수를 사용할 계획이라면 정답을 분리하고 서버에서 채점을 검증하는 구조가 필요하다. 클라이언트가 계산한 점수만으로 신뢰도 높은 평가를 보장할 수는 없다.

참고: [Firebase 필드 접근 제어](https://firebase.google.com/docs/firestore/security/rules-fields), [Firebase Rules 에뮬레이터 테스트](https://firebase.google.com/docs/firestore/security/test-rules-emulator)

### 성능·유지보수

- 대시보드는 최근 최대 16차시에 대해 출결·과제·복습의 3종 실시간 조회와 수강생·질문 조회를 연다. 구현상 최대 50개의 조회 구독이며, 이를 곧바로 비용 50회로 해석하면 안 된다. 실제 비용은 읽은 문서·변경·재연결 등에 달려 있다.
- 현재 작은 반에서 이것만으로 구조를 전면 교체할 이유는 없다. 반·차시가 늘면 기간 제한, 상세 기록의 지연 로딩, 차시별 요약 문서, 목록 페이지 분할부터 검토한다.
- 퀴즈 응시 이력을 펼칠 때 읽는 방식은 적절하다. 대시보드에서 답안·피드백 전체를 읽지 않고 집계에 필요한 요약만 읽도록 발전시킬 수 있다.
- 두 HTML에 인증·업로드·모달·스타일 구현이 중복되어 있다. 공통 유틸리티와 CSS 토큰, 기능별 모듈로 분리하면 한쪽만 수정되는 문제를 줄일 수 있다. 지금 단계에서 특정 프레임워크로 전면 이전할 필요는 없다.
- 기존 스타일 위에 여러 수정 스타일이 누적되어 있어 변경 영향 추적이 어렵다. 화면별 최종 스타일을 정리하고 사용하지 않는 규칙을 제거한다.
- README에 개발 실행법, Firebase 환경 구분, 권한·데이터 구조, 배포·복구 방법을 남긴다. Rules와 필요한 인덱스를 코드로 관리하면 이후 변경을 검토하기 쉬워진다.

참고: [Firebase 실시간 조회 과금 설명](https://firebase.google.com/docs/firestore/pricing)

## 10. 권장 수정 순서와 완료 기준

### 1단계: 기록과 상태 전환 안정화

출결 상태 보존 → 음성 초안 대상 분리 → 초안 복구 → 추가 질문 상태 → 재제출 버전 → 퀴즈 버전을 수정한다. 공통 모달의 Enter 문제와 피드백 수정 형식도 함께 고친다. 실제 권한 설정을 확인하고 핵심 거부·허용 사례를 테스트한다.

**이 단계가 끝나면:** 강사가 화면을 옮기거나 학생이 다시 제출·질문해도 기록이 사라지거나 다른 대상에 붙지 않는다.

### 2단계: 대시보드의 기준과 연결 개선

완료·진행·예정 차시, 배정 대상, 마감 정책, 입력 완성도를 정의한다. 최근 차시 필터와 첫 점수+참여율을 수정하고, 처리 대기 항목을 기존 관리 화면에 연결한다.

**이 단계가 끝나면:** 대시보드의 수치가 무엇을 의미하는지 설명 가능하고, 강사가 수치를 본 뒤 바로 필요한 일을 처리할 수 있다.

### 3단계: 학생 동선과 모바일 정리

새 피드백 우선 노출, 제출 완료 상태, 현재 차시 기본값, 하단 메뉴 정리, 모바일 상단 축소, 입력 라벨·포커스를 개선한다.

**이 단계가 끝나면:** 학생은 들어오자마자 할 일과 받은 답변을 찾고, 강사는 모바일에서도 출결·질문·피드백에 빠르게 접근한다.

### 4단계: 교육적 분석 확장

문항 태그·오답 분석 → 학생별 진행표·포트폴리오 → 말하기·쓰기 평가와 지연 확인 문제 순으로 확장한다. 실제 수업에서 아내가 반복적으로 확인하는 질문에 맞춰 우선순위를 조정한다.

실제 Firebase 인증, 배포된 보안 규칙, 실제 저장·업로드·재생, 스마트폰 마이크, 여러 기기의 동시 수정과 네트워크 단절 복구는 이번 검증에 포함되지 않았다. 현재 결과는 해당 영역의 통과 판정이 아니다.

**추천하는 첫 수정 묶음:** F01~F05의 기록·상태 문제와 메모 입력 문제를 먼저 해결하고, 그 위에 대시보드 집계 기준과 ‘처리할 일’을 올리는 것이다. 그러면 수업 운영의 안정성과 화면의 실용성이 함께 좋아진다.
